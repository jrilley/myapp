# Backend: Telegram-бот + API заявок

Приймає заявки через Telegram-бота, зберігає їх у БД, публікує в Telegram-групу
і віддає на сайт через REST API.

```
Користувач → бот (анкета) → SQLite → ├─ повідомлення в Telegram-групу
                                     └─ GET /api/applications → React-сторінка /applications
```

## Чому один процес

`aiogram` (polling) і FastAPI живуть в одному процесі та одному event loop:
SQLite має один writer, і два окремі процеси регулярно ловили б
`database is locked`. Плюс це один юніт деплою й одна фабрика сесій.
`RUN_BOT=false` піднімає лише API — так працюють тести й CI.

## Запуск

Найпростіше — однією командою з кореня репозиторію: `npm run dev`
(на Windows `.\dev.cmd`). Вона піднімає і бекенд, і сайт; див.
[README у корені](../README.md).

Окремо тільки бекенд:

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env      # заповніть TELEGRAM_BOT_TOKEN та інші значення
alembic upgrade head      # створити/оновити схему
uvicorn app.main:app --reload --port 8000
```

На Windows активація venv інша — `.venv\Scripts\Activate.ps1`, а якщо
PowerShell блокує скрипти, простіше звертатись напряму:
`.venv\Scripts\uvicorn.exe app.main:app --reload --port 8000`.

> **Файли конфігурації тримайте в ASCII.** `alembic.ini` Alembic читає в
> *локальному* кодуванні (на Windows це зазвичай cp1251/cp1252), тому
> кирилиця в ньому валить `alembic` з `UnicodeDecodeError`. На `.env` це не
> поширюється — його читаємо явно як UTF-8.

У dev запити йдуть через `"proxy": "http://localhost:8000"` у `package.json`,
тому CORS не потрібен. Для продакшн-збірки задайте `REACT_APP_API_URL`.

## Робочий і тестовий інстанси

`APP_ENV` обирає файл конфігурації:

| `APP_ENV` | Конфіг | Призначення |
|---|---|---|
| не заданий | `backend/.env` | робочий бот, робоча група, `applications.db` |
| `test` | `backend/.env.test` | тестовий бот, тестова група, `applications.test.db` |

Це єдиний перемикач — далі все (БД, група, CORS) береться з відповідного файлу,
тож інстанси ніде не перетинаються. Запуск описаний у [README в корені](../README.md).

> **Тестовий інстанс має використовувати ОКРЕМОГО бота.** Telegram тримає лише
> один `getUpdates`-потік на токен: два процеси з одним токеном отримають
> `409 Conflict`, і апдейти почнуть випадково розподілятись між ними.

Міграції для тестової БД накочуються окремо — `APP_ENV=test alembic upgrade head`
(на Windows `$env:APP_ENV="test"; .venv\Scripts\alembic.exe upgrade head`).

## Змінні оточення

Усі описані в `.env.example`. Найважливіше:

| Змінна | Призначення |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен від [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_GROUP_CHAT_ID` | ID групи для публікації (від'ємне число) |
| `ADMIN_TELEGRAM_IDS` | Telegram-id адміністраторів через кому |
| `ADMIN_API_TOKEN` | секрет для заголовка `X-Admin-Token` |
| `DATABASE_URL` | за замовчуванням SQLite |
| `RUN_BOT` | `false` — лише API, без polling |

> **Безпека.** `backend/.env` у git не потрапляє. Токен бота ніколи не має
> потрапляти у фронтенд і **ніколи** не повинен мати префікса `REACT_APP_` —
> CRA вшиває такі змінні у публічний бандл у відкритому вигляді.

## Керування ботом

**Основний спосіб — inline-кнопки.** Друкувати команди не потрібно: `/start`
показує меню, і далі все робиться натисканнями.

**Склад меню залежить від користувача** — від його ролі в таблиці `employees`:

| Кнопка | Кому видно | Куди веде |
|---|---|---|
| 🔑 Зареєструватися | незареєстрованим | анкета реєстрації |
| 🚛 Новий рейс | зареєстрованим | десять кроків + підтвердження, рядок у `trips` |
| 🧾 Рейси | зареєстрованим | свої рейси; адмінам — компанії або всі |
| 🚛 Додати автомобіль | адмінам | тягач або причіп із прив'язкою до компанії |
| 🚚 Транспорт | адміну компанії | транспорт своєї компанії |
| 👥 Працівники | адміну компанії | працівники своєї компанії |
| 🏢 Компанії | головному адміну | компанії: картка з редагуванням, а через неї транспорт і працівники |
| 💼 Посади | головному адміну | довідник посад: доступність і додавання нових |
| ℹ️ Довідка | усім | довідка + меню |
| ✖️ Скасувати | усім | висить під кожним кроком анкети |
| 🗑 #N | автору або адміну | видаляє заявку і перемальовує список на місці |

> **Приховування кнопки — не захист.** `callback_data` можна переслати іншій
> людині або згенерувати вручну, тому кожен обмежений хендлер перевіряє право
> при виклику, а не покладається на те, що кнопки не було видно. Це стосується
> і адмінських дій, і кнопки 🗑, і самої анкети заявки.

### Стара анкета заявок вимкнена

`constants.SHOW_APPLICATIONS = False` прибирає з меню «📝 Нова заявка»,
«📋 Мої заявки», «🗂 Усі заявки» та «📊 Статистика», а також команди `/new`
і `/my` зі списку ☰.

Прапорець, а не закоментований код: код лишається живим — компілюється,
лінтується й покритий тестами (фікстура `applications_enabled` вмикає його на
час тесту), — тож повернути анкету означає змінити один рядок, а не
відновлювати те, що встигло зіпсуватись. Читається він у момент виклику
(`constants.SHOW_APPLICATIONS`, а не `from … import SHOW_APPLICATIONS`), тому
перемикається в рантаймі.

Хендлери відмовляють самі, а не покладаються на прибрану кнопку: `callback_data`
з попередніх повідомлень лишається робочою.

**Чого вимкнення не чіпає:** таблицю `applications`, REST API та сайт. Наявні
заявки на місці й далі видно на сайті — прибрана лише робота з ними в боті.

## Реєстрація та ролі

**Рейс може створити лише зареєстрований співробітник.** Реєстрація створює
рядок у `employees`: ПІБ → телефон → додатковий номер (за бажанням) →
компанія (кнопки) → підтвердження.

**Посаду не питаємо.** Новий співробітник завжди отримує посаду **«Водій»** і
роль **«Водій»**; змінює обидві головний адміністратор у картці. Питати посаду
не було сенсу: призначити її собі людина все одно не може, а зайвий крок лише
подовжував анкету. У зведенні перед підтвердженням посаду все ж показуємо —
людина має бачити, ким її запишуть.

Номер запитується кнопкою **«📱 Поділитися номером»** (`request_contact`).
Це вимагає reply-клавіатури: до одного повідомлення можна прикріпити або
inline-, або reply-розмітку, не обидві — тому скасування на цьому кроці
теж reply-кнопка й розпізнається за текстом. Ввести номер вручну так само
можна, якщо ділитися контактом не хочеться.

> **Спільний контакт перевіряється.** Telegram дозволяє надіслати чужий
> контакт зі списку, тому бот звіряє `contact.user_id` з відправником і
> чужий номер не приймає.

Після цього бот питає про додатковий номер. Він необов'язковий і
зберігається в `employees.phone_number2`.

## Права

Права — це **матриця роль × розділ × CRED** у таблиці `role_permissions`, плюс
обсяг: усі компанії / своя компанія / лише свої записи.

| Роль | Компанія | Працівники | Транспорт | Рейси | Обсяг |
|---|---|---|---|---|---|
| Головний адміністратор | CRED | CRED | CRED | CRED | усі компанії |
| Адміністратор компанії | RE | RE | CRED | CRED | своя компанія |
| Менеджер | R | R | — | CRED | своя компанія |
| Логіст | R | R | CRE | CRED | своя компанія |
| Оператор | R | — | — | RE *(лише маси)* | своя компанія |
| Диспетчер | R | — | — | RE *(лише статус)* | своя компанія |
| Водій | — | — | — | R | лише свої рейси |

**C** створення · **R** перегляд · **E** редагування · **D** видалення.

Хендлери питають `access.can(розділ, право)` і не знають ні про назви ролей, ні
про SQL: матрицю один раз читає `AccessMiddleware`. Меню будується з тієї самої
матриці, тож кнопки й перевірки розійтись не можуть — але приховати кнопку
все одно не є захистом, і кожен хендлер перевіряє право ще раз.

**Права на рівні поля.** `role_permissions.fields` звужує E до переліку: у
оператора це `bmass,tmass,nmass`, у диспетчера — `status`. Тому саме право E ще
не означає, що можна чіпати все: перед кожним редактором стоїть
`access.may_edit_field`.

**Головного адміністратора в таблиці немає взагалі.** Його доступ — окремий
об'єкт у коді (`access.FULL`), щоб зняти його не могла ні міграція, ні описка в
рядку. Це ж стосується `ADMIN_TELEGRAM_IDS`.

**Матриця змінюється міграцією, не з бота.** Право змінювати права — це те, з
чого починаються тихі підвищення. Головний адмін може її переглянути:
🔑 Ролі й права.

Значення живуть у двох місцях — `app/permissions.py` (звідки їх читають тести)
і міграція `6a3a66f4347b` (звідки вони потрапляють у базу). Копія в міграції —
норма, вона фіксує стан на момент створення; щоб копії не розійшлись мовчки, є
тест `test_code_and_migration_agree`.

**Що з цього випливає:**

- Адміністратор компанії веде компанію, людей, транспорт і рейси — але не
  довідники посад і ролей: вони спільні для всіх компаній.
- Машини заводять адміністратор компанії й логіст; видаляє лише адміністратор.
- Менеджер і логіст створюють рейси; оператор і диспетчер їх лише правлять, кожен
  у своїй частині; водій — читає.
- Роль «Користувач» більше не видається: усіх, хто на ній був, міграція перевела
  на «Водій» — рівний за правами набір.

> **`ADMIN_TELEGRAM_IDS` лишається аварійним входом.** Без нього виникає
> замкнене коло: адміном робить роль у `employees`, але поки немає жодної
> компанії, ніхто не може зареєструватись — а компанію заводить тільки
> головний адмін. Тому id зі списку в `.env` вважається головним
> адміністратором навіть без рядка в `employees`. Після того, як перший
> справжній адмін зареєстрований, список можна спорожнити.

Хто є хто, визначає `app/bot/access.py`; `AccessMiddleware` рахує це один раз
на апдейт і кладе готовий об'єкт `Access` у хендлери.

### Навігація по компанії

Транспорт і працівники завжди належать компанії, тож і дивляться їх у її межах.
Шлях різний залежно від того, скільки компаній бачить користувач:

```
Головний адмін:      🏢 Компанії → компанія → 🚚 Транспорт → тягачі/причепи → список
                                            → 👥 Працівники → список
Адміністратор компанії:  🚚 Транспорт → тягачі/причепи → список
                         👥 Працівники → список
```

Підписи кнопок: транспорт — `brand - license_plate`, працівники —
`посада, ПІБ`.

> **Межа компанії тримається в коді, а не в меню.** `resolve_company_id()`
> для адміністратора компанії повертає **його** компанію незалежно від того,
> що прийшло в `callback_data`. Підставити чужий id і побачити чужі машини
> чи працівників не вийде — на це є тести.

### Керування співробітниками

Список працівників відкриває картку з ПІБ, телефонами, компанією, посадою,
роллю та Telegram-id. З картки редагується будь-яке поле: текстові через ввід,
довідникові (компанія, посада, роль) — вибором зі списку, який застосовується
одразу.

> **Роль і компанію змінює лише головний адміністратор.** Інакше
> адміністратор компанії міг би підвищити свою людину до головного або
> перекинути працівника в чужу компанію. Решту полів він редагує в межах
> своєї компанії.

> **Власну роль змінити не можна.** Інакше головний адміністратор одним
> натисканням знімає з себе доступ і повернути його вже нічим — крім
> `ADMIN_TELEGRAM_IDS` або правки БД руками.

Транспорт має власну картку з маркою, моделлю, номером і компанією; з неї
редагуються перші три поля. При зміні номера перевіряється унікальність, але
власний номер запису конфліктом не вважається.

«💼 Посади» показує довідник — кнопкою на кожну посаду, з підписом
`назва — самостійно / лише адмін`. Звідти відкривається картка: чи можна обрати
посаду при реєстрації та скільки людей на ній зараз. Додавання нової: назва →
доступність. Назва унікальна, і дублікат відсіюється на кроці вводу, а не
помилкою БД — причому двічі, бо поки анкета відкрита, назву міг зайняти хтось
інший.

«🏢 Компанії» → картка компанії: назва, код, адреса та **робочий чат**. Усі
чотири поля редагуються звідти ж. Робочий чат (`company.company_chat_id`) — це
група в Telegram, куди бот дублює створені рейси; його можна лишити порожнім і
вказати пізніше.

### Додавання транспорту

Кнопка одна, а таблиць дві, тому першим кроком бот питає тип: **тягач** →
`truck`, **причіп** → `trailer`. Далі — марка, модель, держномер (кожне поле
окремо), потім зведення введеного й підтвердження.

**Компанія береться по-різному залежно від ролі:**

| Роль | Звідки компанія |
|---|---|
| Головний адміністратор | обирає зі списку; підпис кнопки — `name - tax_id` |
| Адміністратор компанії | з його власного запису в `employees` |

Адміністратор компанії кроку вибору не бачить взагалі — інакше він міг би
завести машину чужій компанії.

Держномер зводиться до верхнього регістру й перевіряється на унікальність
двічі: на вводі та ще раз перед вставкою, бо поки анкета відкрита, номер
міг зайняти хтось інший.

## Рейси

Рейс — заявка на перевезення за однією ТТН, таблиця `trips`. Заводить його
**логіст**: будь-який зареєстрований співробітник, у якого є компанія.

Анкета — десять кроків і підтвердження:

```
ТТН → дата прибуття (календар) → компанія-експортер (кнопки)
    → тягач → номер тягача → причіп → тип причепа → номер причепа
    → культура → водій (кнопки) → перевірка
```

**Водія обирають зі складу компанії** — кнопка `посада, ПІБ`. Себе логіст у
списку не бачить. Поруч завжди є «✍️ Ввести вручну»: рейс може виконувати
найманий перевізник, якого в `employees` немає, — тоді додається крок телефону,
а `driver_id` лишається порожнім. ПІБ і телефон копіюються в рейс у будь-якому
разі: рейс — документ, і він має лишитись читабельним, якщо людина піде з
компанії.

### Куди йде створений рейс

| Куди | Коли |
|---|---|
| водієві в приват | якщо водія обрано зі списку |
| у робочий чат компанії-замовника | якщо `company.company_chat_id` заповнено |

`chat_id` і `chat_message_id` зберігаються в самому рейсі — без них його не
прибрати з чату при видаленні. Chat id дублюється навмисно: робочий чат компанії
могли змінити, і тоді правка пішла б у новий чат, а повідомлення висить у старому.

**Розсилка не може скасувати рейс.** Він уже в базі; Telegram буває недоступний,
водій міг не запускати бота (тоді Telegram узагалі не дозволяє писати першим),
бота могли прибрати з групи. Тому кожен збій лише дописується в звіт логісту —
мовчати не можна, інакше він вважатиме, що водій рейс отримав.

> **Група, що стала супергрупою, змінює id.** Telegram відповідає помилкою
> `TelegramMigrateToChat` і в ній же каже новий id; старий мертвий назавжди.
> `publisher.send` повторює надсилання туди один раз і повертає той чат, у
> який повідомлення справді пішло, — а хендлер записує новий id у
> `company.company_chat_id`. Без цього кожен наступний рейс упирався б у той
> самий глухий кут, і виправляти довелось би руками.

**Чотири поля бот не питає** — вони підставляються з `employees` того, хто
заповнює форму: компанія-замовник (`client_company_id`), ПІБ, телефон і
Telegram-id логіста. Тому підставити чужу компанію нема чим: у формі просто
немає такого кроку.

Дата обирається в календарі, а не вводиться текстом, — так у колонці не
з'явиться двох написань однієї дати. Номери причепа й тягача звіряються між
собою: однаковими вони бути не можуть.

**Хто які рейси бачить:**

| Роль | Видимість |
|---|---|
| Головний адміністратор | усі рейси |
| Адміністратор компанії | рейси своєї компанії (`client_company_id`) |
| Користувач | власні: `created_by` **або** `driver_id` — це він |

**Водій бачить, але не редагує.** Рейс — це завдання, яке йому видали, а не його
документ, тому кнопок редагування в картці немає, і підроблений `callback_data`
теж відхиляється (`_may_view` проти `_may_edit` у `handlers/trips.py`). Якщо
знадобиться, щоб водій сам ставив час заїзду й виїзду, — межа проходить саме
тут.

Межа перевіряється й при відкритті рейсу за прямим id, а не лише при побудові
списку: `callback_data` можна підробити. Обсяг видимого обчислює
`actions.render_trips` за роллю — у `callback_data` немає нічого, чим його
можна було б розширити.

**Аудит.** Редагування пише `edited_by` і `updated_at`, видалення —
`deleted_by` і `deleted_at`; рядок не стирається. Обидві пари проставляє
`repository.update_trip` / `soft_delete_trip`, а не хендлери: інакше досить
було б додати один новий редактор і забути про аудит.

**Відхилення від наданого опису таблиці:**

| Поле | В описі | У схемі | Чому |
|---|---|---|---|
| `client_company`, `exporter_company` | `TEXT` | `INTEGER` + FK на `company.id` | у полі лежить `company.id`; зв'язок має бути справжнім, інакше його не перевірити й не зджойнити |
| `edited_by` | `NOT NULL` | nullable | той самий опис каже «при створенні порожнє» — виконати обидві вимоги неможливо |
| `logist_tg` | немає в DDL | `BIGINT NOT NULL` | є в описі поведінки: щоб із рейсу можна було написати логісту |

Дані логіста (`logist_fullname`, `logist_phone_number`, `logist_tg`) дублюють
`employees` навмисно, попри наявний FK `created_by`: рейс — документ, і він має
лишитись читабельним, якщо співробітник змінить прізвище чи піде з компанії.
FK відповідає на «хто це зараз», копія — на «хто це був тоді».

Дати й час зберігаються текстом, як у вихідному описі, але з фіксованими
форматами — щоб сортування рядком збігалося з хронологією:

| Колонка | Формат |
|---|---|
| `arrival_date` | `РРРР-ММ-ДД` |
| `datetime_entry`, `datetime_departure` | `РРРР-ММ-ДД ГГ:ХХ`, місцевий час |
| `created_at`, `updated_at`, `deleted_at` | ISO-8601 UTC, проставляє репозиторій |

`created_at` не сортувальне поле — списки йдуть за датою прибуття, — але без
нього неможливо сказати, коли рейс з'явився: `updated_at` і `deleted_at` при
створенні порожні.

`status` — текст, а не enum: додати статус має бути зміною константи
(`models.TRIP_STATUS_NEW` і сусіди), а не міграцією схеми. При створенні
завжди «Створено».

### Пагінація

Усі списки гортаються рядком «‹ Назад · 2 / 5 · Далі ›». Розміри сторінок
різні: заявки багатослівні, довідники — ні.

| Список | На сторінці |
|---|---|
| Мої заявки, Усі заявки | 5 |
| Рейси | 6 |
| Користувачі | 8 |
| Посади, Компанії, Транспорт | 10 |

Гортання **редагує те саме повідомлення**, а не надсилає нове. Вид списку й
зсув приходять у `callback_data`, тож обидва можна підмінити — тому
`on_page` перевіряє права заново для кожного виду, а не покладається на те,
що кнопку показали лише тому, кому слід. Формат — `page:<вид>[:<параметри>]:<зсув>`,
зсув завжди останній, тож списки з додатковими параметрами розбираються тим
самим хендлером.

> **Заявки (`applications`) із компаніями не пов'язані.** «Адміністратор
> компанії» бачить усі заявки, а не лише заявки своєї компанії. Рейсів це не
> стосується — там межа компанії є, див. нижче.

Команди лишаються робочими для тих, кому зручніше текстом, і показані в меню ☰
клієнта Telegram (`set_my_commands` при старті):

| Команда | Хто | Дія |
|---|---|---|
| `/start`, `/help` | усі | меню; `/start` скидає незавершену анкету |
| `/new` | усі | почати анкету |
| `/cancel` | усі | перервати заповнення |
| `/my` | усі | свої заявки |
| `/delete <id>` | власник або адмін | видалити заявку |

Кнопка 🗑 і `/delete` виконують одну функцію з `app/bot/actions.py`, тож права
доступу перевіряються в одному місці й не можуть розійтись.

Анкета: ПІБ → контакт → категорія (кнопки) → опис → підтвердження.
При невалідному вводі бот лишається на тому ж кроці, вже введені відповіді
не губляться.

## API

| Метод | Шлях | Доступ |
|---|---|---|
| `GET` | `/api/health` | публічно |
| `GET` | `/api/applications?status=&limit=&offset=` | публічно |
| `GET` | `/api/applications/{id}` | публічно |
| `GET` | `/api/admin/applications?include_deleted=` | `X-Admin-Token` |
| `DELETE` | `/api/applications/{id}` | `X-Admin-Token` |

Документація OpenAPI — на `/docs`.

**Приватність.** Контакт автора заявки віддається **публічно** — і в групу, і в
`GET /api/applications`, і на сайт. Це свідоме рішення: заявка без способу
зв'язатися з автором на сайті марна.

Наслідок, про який варто пам'ятати: контакти доступні будь-кому, включно з
пошуковими роботами й збирачами баз. Тому бот попереджає користувача двічі —
на кроці «залиште контакт» і в підсумку перед підтвердженням, — щоб контакт
залишали усвідомлено. Якщо змінити це рішення, приберіть `contact` з
`ApplicationPublic` у `app/schemas.py` **і** поверніть відповідні формулювання
в `app/bot/handlers/form.py`.

Внутрішні поля (`telegram_user_id`, `group_chat_id`, `group_message_id`,
`deleted_at`) публічно не віддаються — вони потрібні лише механіці публікації.
Їх повертає `/api/admin/applications`.

**`X-Admin-Token` — це спільний секрет, а не повноцінна авторизація**: немає
ролей, ротації й аудиту. Достатньо, щоб сторонній не видалив заявку; коли
з'являться справжні акаунти адміністраторів, це місце треба замінити.

## Видалення

Видалення **м'яке**: проставляються `deleted_at` і `status='deleted'`, запис
лишається в БД, але зникає з публічних вибірок. Заявки — це персональні дані
й історія звернень, тож безповоротне стирання однією командою в чаті надто
легко зробити помилково.

Повідомлення в групі прибирається best-effort: Telegram дозволяє боту
видаляти повідомлення лише близько 48 годин, тому при невдачі текст
замінюється на «Заявку видалено». Збій у Telegram не скасовує видалення в БД.

## Модерація (наперед)

Модерації зараз немає — заявка одразу `published`. Поле `status`
(`pending`/`published`/`rejected`/`deleted`) вже є в схемі й в API, тож
увімкнути модерацію можна **без міграції**: достатньо передавати
`status=ApplicationStatus.pending` у `repository.create_application`
(виклик — у `app/bot/handlers/form.py`) і додати адмінські кнопки схвалення.

## Структура БД

Повна структура — [`docs/schema.json`](../docs/schema.json): таблиці, колонки з
типами під SQLite і PostgreSQL, nullable, індекси, значення enum, ревізія
Alembic і те, які колонки віддає публічний API.

Файл **генерується**, а не пишеться руками:

```bash
python scripts/dump_schema.py           # перегенерувати
python scripts/dump_schema.py --check   # чи не відстав від моделі
```

Джерело — `app/models.py`; описи колонок беруться з `doc=` у самій моделі,
а перелік публічних полів виводиться з `app/schemas.py`. Тому документація
не може розійтися з кодом. `doc=` — метадані рівня Python, у DDL вони не
йдуть і міграцій не створюють (перевірено `alembic check`).

Після зміни моделі: `alembic revision --autogenerate` → `alembic upgrade head`
→ `python scripts/dump_schema.py`.

> **На час міграцій перевірка зовнішніх ключів вимикається** (`migrations/env.py`).
> Batch-режим перебудовує таблицю через `CREATE tmp → DROP стара → RENAME`, а
> `DROP` батьківської таблиці з увімкненими ключами SQLite не пропускає. Прагма
> ставиться на подію `connect`, а не окремим запитом: `PRAGMA` не діє всередині
> транзакції, а будь-який запит на з'єднанні SQLAlchemy її відкриває — і тоді
> коміт міграції дістається зовнішній транзакції, якої ніхто не комітить, тож
> зміни мовчки відкочуються при закритті. Після міграцій виконується
> `PRAGMA foreign_key_check`: якщо міграція лишила посилання в нікуди, запуск
> падає з помилкою, а не тихо йде далі.

Графічна версія — [`docs/schema.pdf`](../docs/schema.pdf), п'ять аркушів:
маршрут заявки, таблиця `applications`, компанії й співробітники, ролі й права,
рейс.
Генерується `scripts/make_schema_pdf.py`.

Таблиць дев'ять: `applications`, `company`, `positions`, `roles`,
`role_permissions`, `employees`, `truck`, `trailer`, `trips`.

## Журнал подій — план

[`docs/logging-plan.pdf`](../docs/logging-plan.pdf), два аркуші: звідки беруться
події та таблиця `events`. **Коду ще немає** — це план, тому файл не звіряється
з моделями, його джерело — сам `scripts/make_logging_pdf.py`.

Коротко: події пише окремий middleware, а не хендлери, бо через нього проходить
кожен апдейт — логування неможливо забути при додаванні нового екрана. Запис
події не має права зламати дію: коміт окремий, помилка гаситься. Значень, які
ввела людина, у журнал не потрапляє — лише імена полів і результат.

Палітра, шрифти й клас `Sheet` спільні для обох PDF — вони живуть у
`scripts/_sheet.py`, щоб схеми не розійшлися у вигляді.

## Тести

```bash
cd backend && ./.venv/bin/pytest
```

Мережі не торкаються: БД — SQLite in-memory, публікація в Telegram підмінена
`FakePublisher`, FSM-хендлери викликаються напряму з фейковими
`Message`/`CallbackQuery` і реальним `FSMContext` на `MemoryStorage`.

## Перехід на PostgreSQL

1. `pip install asyncpg`
2. `DATABASE_URL=postgresql+asyncpg://user:pass@host:5432/db`
3. `alembic upgrade head`

Шар доступу до БД (`app/repository.py`) не містить SQLite-специфіки, тож
змін у коді не потрібно.
