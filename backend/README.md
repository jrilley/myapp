# Backend: Telegram-бот + API заявок

Приймає заявки через Telegram-бота, зберігає їх у БД, публікує в Telegram-групу
і віддає на сайт через REST API.

```
Користувач → бот (анкета) → SQLite → ├─ повідомлення в Telegram-групу
                                     └─ GET /api/applications → React-сторінка /applications
```

## Чому один процес

`aiogram` (polling) і FastAPI живуть в одному процесі та одному event loop:
SQLite має один writer, і два окремі процеси регулярно ловили б
`database is locked`. Плюс це один юніт деплою й одна фабрика сесій.
`RUN_BOT=false` піднімає лише API — так працюють тести й CI.

## Запуск

Найпростіше — однією командою з кореня репозиторію: `npm run dev`
(на Windows `.\dev.cmd`). Вона піднімає і бекенд, і сайт; див.
[README у корені](../README.md).

Окремо тільки бекенд:

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

cp .env.example .env      # заповніть TELEGRAM_BOT_TOKEN та інші значення
alembic upgrade head      # створити/оновити схему
uvicorn app.main:app --reload --port 8000
```

На Windows активація venv інша — `.venv\Scripts\Activate.ps1`, а якщо
PowerShell блокує скрипти, простіше звертатись напряму:
`.venv\Scripts\uvicorn.exe app.main:app --reload --port 8000`.

> **Файли конфігурації тримайте в ASCII.** `alembic.ini` Alembic читає в
> *локальному* кодуванні (на Windows це зазвичай cp1251/cp1252), тому
> кирилиця в ньому валить `alembic` з `UnicodeDecodeError`. На `.env` це не
> поширюється — його читаємо явно як UTF-8.

У dev запити йдуть через `"proxy": "http://localhost:8000"` у `package.json`,
тому CORS не потрібен. Для продакшн-збірки задайте `REACT_APP_API_URL`.

## Робочий і тестовий інстанси

`APP_ENV` обирає файл конфігурації:

| `APP_ENV` | Конфіг | Призначення |
|---|---|---|
| не заданий | `backend/.env` | робочий бот, робоча група, `applications.db` |
| `test` | `backend/.env.test` | тестовий бот, тестова група, `applications.test.db` |

Це єдиний перемикач — далі все (БД, група, CORS) береться з відповідного файлу,
тож інстанси ніде не перетинаються. Запуск описаний у [README в корені](../README.md).

> **Тестовий інстанс має використовувати ОКРЕМОГО бота.** Telegram тримає лише
> один `getUpdates`-потік на токен: два процеси з одним токеном отримають
> `409 Conflict`, і апдейти почнуть випадково розподілятись між ними.

Міграції для тестової БД накочуються окремо — `APP_ENV=test alembic upgrade head`
(на Windows `$env:APP_ENV="test"; .venv\Scripts\alembic.exe upgrade head`).

## Змінні оточення

Усі описані в `.env.example`. Найважливіше:

| Змінна | Призначення |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен від [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_GROUP_CHAT_ID` | ID групи для публікації (від'ємне число) |
| `ADMIN_TELEGRAM_IDS` | Telegram-id адміністраторів через кому |
| `ADMIN_API_TOKEN` | секрет для заголовка `X-Admin-Token` |
| `DATABASE_URL` | за замовчуванням SQLite |
| `RUN_BOT` | `false` — лише API, без polling |

> **Безпека.** `backend/.env` у git не потрапляє. Токен бота ніколи не має
> потрапляти у фронтенд і **ніколи** не повинен мати префікса `REACT_APP_` —
> CRA вшиває такі змінні у публічний бандл у відкритому вигляді.

## Керування ботом

**Основний спосіб — inline-кнопки.** Друкувати команди не потрібно: `/start`
показує меню, і далі все робиться натисканнями.

**Склад меню залежить від користувача** — від його ролі в таблиці `employees`:

| Кнопка | Кому видно | Куди веде |
|---|---|---|
| 🔑 Зареєструватися | незареєстрованим | анкета реєстрації |
| 📝 Нова заявка | зареєстрованим | починає анкету заявки |
| 📋 Мої заявки | зареєстрованим | свої заявки, у кожної — кнопка 🗑 |
| 🗂 Усі заявки | адмінам | останні 10 заявок усіх користувачів, з автором |
| 📊 Статистика | адмінам | кількість заявок за статусами |
| 👥 Користувачі | головному адміну | список співробітників, картка кожного, редагування |
| 💼 Посади | головному адміну | довідник посад і додавання нових |
| 🏢 Компанії | головному адміну | список компаній і додавання нових |
| ℹ️ Довідка | усім | довідка + меню |
| ✖️ Скасувати | усім | висить під кожним кроком анкети |
| 🗑 #N | автору або адміну | видаляє заявку і перемальовує список на місці |

> **Приховування кнопки — не захист.** `callback_data` можна переслати іншій
> людині або згенерувати вручну, тому кожен обмежений хендлер перевіряє право
> при виклику, а не покладається на те, що кнопки не було видно. Це стосується
> і адмінських дій, і кнопки 🗑, і самої анкети заявки.

## Реєстрація та ролі

**Заявку може подати лише зареєстрований співробітник.** Реєстрація створює
рядок у `employees`: ПІБ → телефон → додатковий номер (за бажанням) →
компанія (кнопки) → посада (кнопки) → підтвердження. Нового користувача
записуємо з роллю **«Користувач»**; підвищує її адміністратор — поки що
прямо в БД.

Номер запитується кнопкою **«📱 Поділитися номером»** (`request_contact`).
Це вимагає reply-клавіатури: до одного повідомлення можна прикріпити або
inline-, або reply-розмітку, не обидві — тому скасування на цьому кроці
теж reply-кнопка й розпізнається за текстом. Ввести номер вручну так само
можна, якщо ділитися контактом не хочеться.

> **Спільний контакт перевіряється.** Telegram дозволяє надіслати чужий
> контакт зі списку, тому бот звіряє `contact.user_id` з відправником і
> чужий номер не приймає.

Після цього бот питає про додатковий номер. Він необов'язковий і
зберігається в `employees.phone_number2`.

Права визначає роль у `employees`, а не `.env`:

| Роль | Що може |
|---|---|
| Головний адміністратор | усе, зокрема заводити компанії |
| Адміністратор компанії | усі заявки, статистика, видалення чужих заявок |
| Користувач | свої заявки |

> **`ADMIN_TELEGRAM_IDS` лишається аварійним входом.** Без нього виникає
> замкнене коло: адміном робить роль у `employees`, але поки немає жодної
> компанії, ніхто не може зареєструватись — а компанію заводить тільки
> головний адмін. Тому id зі списку в `.env` вважається головним
> адміністратором навіть без рядка в `employees`. Після того, як перший
> справжній адмін зареєстрований, список можна спорожнити.

Хто є хто, визначає `app/bot/access.py`; `AccessMiddleware` рахує це один раз
на апдейт і кладе готовий об'єкт `Access` у хендлери.

### Керування співробітниками

«👥 Користувачі» відкриває список; кожен рядок — кнопка, що показує картку з
ПІБ, телефоном, компанією, посадою, роллю та Telegram-id. З картки редагується
будь-яке поле: текстові через ввід, довідникові (компанія, посада, роль) —
вибором зі списку, який застосовується одразу.

> **Власну роль змінити не можна.** Інакше головний адміністратор одним
> натисканням знімає з себе доступ і повернути його вже нічим — крім
> `ADMIN_TELEGRAM_IDS` або правки БД руками.

«💼 Посади» показує довідник і дозволяє додати нову. Назва унікальна, і
дублікат відсіюється на кроці вводу, а не помилкою БД.

### Пагінація

Усі списки гортаються рядком «‹ Назад · 2 / 5 · Далі ›». Розміри сторінок
різні: заявки багатослівні, довідники — ні.

| Список | На сторінці |
|---|---|
| Мої заявки, Усі заявки | 5 |
| Користувачі | 8 |
| Посади, Компанії | 10 |

Гортання **редагує те саме повідомлення**, а не надсилає нове. Вид списку й
зсув приходять у `callback_data`, тож обидва можна підмінити — тому
`on_page` перевіряє права заново для кожного виду, а не покладається на те,
що кнопку показали лише тому, кому слід.

> **Ролі поки не розмежовані за компаніями.** «Адміністратор компанії» бачить
> усі заявки, а не лише заявки своєї компанії — заявки з компаніями ще ніяк
> не пов'язані.

Команди лишаються робочими для тих, кому зручніше текстом, і показані в меню ☰
клієнта Telegram (`set_my_commands` при старті):

| Команда | Хто | Дія |
|---|---|---|
| `/start`, `/help` | усі | меню; `/start` скидає незавершену анкету |
| `/new` | усі | почати анкету |
| `/cancel` | усі | перервати заповнення |
| `/my` | усі | свої заявки |
| `/delete <id>` | власник або адмін | видалити заявку |

Кнопка 🗑 і `/delete` виконують одну функцію з `app/bot/actions.py`, тож права
доступу перевіряються в одному місці й не можуть розійтись.

Анкета: ПІБ → контакт → категорія (кнопки) → опис → підтвердження.
При невалідному вводі бот лишається на тому ж кроці, вже введені відповіді
не губляться.

## API

| Метод | Шлях | Доступ |
|---|---|---|
| `GET` | `/api/health` | публічно |
| `GET` | `/api/applications?status=&limit=&offset=` | публічно |
| `GET` | `/api/applications/{id}` | публічно |
| `GET` | `/api/admin/applications?include_deleted=` | `X-Admin-Token` |
| `DELETE` | `/api/applications/{id}` | `X-Admin-Token` |

Документація OpenAPI — на `/docs`.

**Приватність.** Контакт автора заявки віддається **публічно** — і в групу, і в
`GET /api/applications`, і на сайт. Це свідоме рішення: заявка без способу
зв'язатися з автором на сайті марна.

Наслідок, про який варто пам'ятати: контакти доступні будь-кому, включно з
пошуковими роботами й збирачами баз. Тому бот попереджає користувача двічі —
на кроці «залиште контакт» і в підсумку перед підтвердженням, — щоб контакт
залишали усвідомлено. Якщо змінити це рішення, приберіть `contact` з
`ApplicationPublic` у `app/schemas.py` **і** поверніть відповідні формулювання
в `app/bot/handlers/form.py`.

Внутрішні поля (`telegram_user_id`, `group_chat_id`, `group_message_id`,
`deleted_at`) публічно не віддаються — вони потрібні лише механіці публікації.
Їх повертає `/api/admin/applications`.

**`X-Admin-Token` — це спільний секрет, а не повноцінна авторизація**: немає
ролей, ротації й аудиту. Достатньо, щоб сторонній не видалив заявку; коли
з'являться справжні акаунти адміністраторів, це місце треба замінити.

## Видалення

Видалення **м'яке**: проставляються `deleted_at` і `status='deleted'`, запис
лишається в БД, але зникає з публічних вибірок. Заявки — це персональні дані
й історія звернень, тож безповоротне стирання однією командою в чаті надто
легко зробити помилково.

Повідомлення в групі прибирається best-effort: Telegram дозволяє боту
видаляти повідомлення лише близько 48 годин, тому при невдачі текст
замінюється на «Заявку видалено». Збій у Telegram не скасовує видалення в БД.

## Модерація (наперед)

Модерації зараз немає — заявка одразу `published`. Поле `status`
(`pending`/`published`/`rejected`/`deleted`) вже є в схемі й в API, тож
увімкнути модерацію можна **без міграції**: достатньо передавати
`status=ApplicationStatus.pending` у `repository.create_application`
(виклик — у `app/bot/handlers/form.py`) і додати адмінські кнопки схвалення.

## Структура БД

Повна структура — [`docs/schema.json`](../docs/schema.json): таблиці, колонки з
типами під SQLite і PostgreSQL, nullable, індекси, значення enum, ревізія
Alembic і те, які колонки віддає публічний API.

Файл **генерується**, а не пишеться руками:

```bash
python scripts/dump_schema.py           # перегенерувати
python scripts/dump_schema.py --check   # чи не відстав від моделі
```

Джерело — `app/models.py`; описи колонок беруться з `doc=` у самій моделі,
а перелік публічних полів виводиться з `app/schemas.py`. Тому документація
не може розійтися з кодом. `doc=` — метадані рівня Python, у DDL вони не
йдуть і міграцій не створюють (перевірено `alembic check`).

Після зміни моделі: `alembic revision --autogenerate` → `alembic upgrade head`
→ `python scripts/dump_schema.py`.

## Тести

```bash
cd backend && ./.venv/bin/pytest
```

Мережі не торкаються: БД — SQLite in-memory, публікація в Telegram підмінена
`FakePublisher`, FSM-хендлери викликаються напряму з фейковими
`Message`/`CallbackQuery` і реальним `FSMContext` на `MemoryStorage`.

## Перехід на PostgreSQL

1. `pip install asyncpg`
2. `DATABASE_URL=postgresql+asyncpg://user:pass@host:5432/db`
3. `alembic upgrade head`

Шар доступу до БД (`app/repository.py`) не містить SQLite-специфіки, тож
змін у коді не потрібно.
